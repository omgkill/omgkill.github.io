Disruptor总结笔记

by 啊沉
2024-11-21
约 1771 字 - 预计阅读 4 分钟
Disruptor

单一生产者/单一消费者(batch)逻辑

生产者

  • 申请序号 # 序号可以是普通字段
  • 等待有效序号 # 确保不会追尾
  • 获取event，然后存入数据
  • 完成，修改游标 #游标需要屏障

消费者

  • 收到通知
  • 生产者游标 与（当前消费者游标值 + 1）判断
  • 获取所有event
  • 遍历执行
  • 修改消费者游标 #游标需要屏障

其他点

  • 确保有序性，但是不能确保立即的可见性
    • 我们平时在使用volatile修饰的字段的时候，大部分都是简单的赋值与读取操作。大家都觉得这样使用比加锁读写还是快多了。其实volatile还有更快的方式。那就是使用UNSAFE.putOrderedLong来对一个volatile变量赋值。其可以确保有序性，但是不能确保立即的可见性。但是它却可以提供比直接对volatile赋值更好的性能。因为它不需要却可见性，也就不涉及到缓存行立即刷新到主存，也不涉及到其他读取了该变量的缓存行的L1或者L2j级缓存失效。所以，在我们使用volatile的时候，如果有些场景只是需要确保有序性，而不需要可见性，则可以考虑使用unsafe.putOrderedXXX来修改volatile变量。

从上面可以看出，做了那些优化吗。 相对于blockArrayQueue

  • 锁的消失

    • blockarray加锁，确保了queue的大小有界，不会超出
    • disruptor通过游标，限制了互相竞争。而游标是通过cas保证正确性

  • 数据结构

    • ringbuffer提前初始化
    • 所有的sequence需要填充
    • 使用环形，并且通过余数来计算slot
      • 逻辑单一更简单。操作也更方便

  • cacheline 优化

    • sequence 使用了填充。 且是原子类

      • 没有自增操作，都是set and get

        • 都不是原子操作。只是用来做屏障？？？
        • 那为什么使用原子类
          • volatile 变量的读写虽然比锁快，但仍然涉及缓存一致性协议和可能的内存屏障，这在某些情况(高并发)下可能成为性能瓶颈。
          • CAS 操作通常直接在硬件层面实现，能够提供比 volatile 更高的性能，尤其是在高并发环境下。

      • 哪写地方使用了sequence，以及作用是什么

        • 消费者游标
          • 多个process共享一个event
          • pool process 独享一个event。
          • 共同原因
            • 因为生产者放入entry时，需要在生产者线程判断游标是否循环 - 多线程读
            • 如果有barrier event(先后依赖的消费者)，那也需要在多个线程get - 多线程读
        • 生产者游标
          • 消费者读取游标 - 多线程读
          • 也是多个生产者线程改 - 多线程改
            • 通过忙等待处理的
        • 生产者序号
          • 因为多个生产者（多个线程）需要先抢唯一的序号。也就是在多个线程修改
    • PaddedLong， 填充，但是普通变量
      • 单个线程使用
      • 有个问题：为什么填充值是volatile
        • 编译器有时会优化掉看似无用的字段。使用volatile关键字可以确保编译器不会优化掉这些填充字段，因为它们可能被视为对多线程环境下的内存可见性有重要作用。
        • volatile关键字的一个主要作用是确保变量的修改对所有线程立即可见。虽然填充字段本身不需要这种可见性，但使用volatile可以确保这些字段在JVM层面不会被优化或重排序。这对于保持填充字段在内存中的存在和防止伪共享是至关重要的。
        • 除了内存可见性，volatile还防止了指令重排序，这可以确保在多线程环境中，对PaddedLong字段的访问不会因优化而被重新排序，从而保持预期的内存布局和访问模式。
    • PaddedAtomicLong 填充，原子
      • 多个线程使用

  • 消费者序号

    • pool process 独享一个event。
      • 当pool consumer（多个一样的消费者），就需要抢序号。也就是在多个线程修改 - 多线程改‘

问题

  • ringbuffer如何确保跨线程一致性

    • 读写屏障？？
    • 特点
      • final修饰

  • 一个特性就是先申请序号，然后再等待slot，再执行。 同时确保按照序号先后执行，

    • 放入操作，如果没到就忙等待
    • 消费操作是，如果没等到重新进入await

  • 问题

    • 这个序号操作，与 加锁有什么区别，或者说，优化了哪些

  • 理解

    • 我一开始以为，消费者是多个相同的hanler，然后分布在不同线程。然后每个消费者都要争抢下一个有效的slot。
      • 后来发现不是。消费者是多个不同的handler，然后各自跟踪生产者的消息，一有消息，各自执行各自的
      • 确实为什么要把相同的逻辑放到多个线程执行呢。
        • 这样很有可能修改相同的字段，就要加锁了
    • 理解没有问题，消费者模式分两种类型
      • 一种线程pool池，执行同一个逻辑。这个就是我上面说的。比较适合io处理的
      • 另一种就是一个事件触发多个不同逻辑。每个逻辑执行自己的顺序
