Skynet配置热更

by 啊沉
2025-02-26
约 998 字 - 预计阅读 2 分钟
Skynet

方案

  • 小表多key
  • 使用sharetable.query() ,避免代码中引用配置
  • 使用玩家agent缓存池，提前加载。
    • 避免登录玩家多时，需要加载大量配置
  • 每个玩家agent初始化，加载所有配置缓存
  • 配置更新时，只更新修改的配置
  • 配置更新时，使用组播所有玩家agent
 1感谢大家的建议，我总结了下：
 2
 3配置表管理方式：
 41、小表多 key
 5优点：使用灵活，服务按需求初始化使用，更新也比较轻量
 6缺点：因为一个进程中 sharetable 服务只有一个，如果使用动态启动和释放的服务（如每个玩家一个 agent），在并发启动时，服务数量越多，服务使用的配置表越多，启动的时间越久。
 7
 82、大表少 key（极端情况所有配置表一个 key）
 9优点：服务初始化配置表速度快。
10缺点：不适合使用 sharetable.update 热更新
11
12热更新方式：
131、使用 sharetable.query 热更新
14优点：热更新到所有服务速度很快，不需要替换数据，也不会引起内存上涨
15缺点：使用时要从配置表的 root 进行索引，不可引用到 local 变量使用
16
172、使用 sharetable.update 热更新
18优点：使用更灵活，可以保存配置到 local 变量
19缺点：配置中的 table 数量越多，内存上涨越大，替换数据的时间越长。内存上涨是 sharetable.update 中 replace_map 和 resolve_replace() 引起。10w+ table 每个服务上涨 5m 左右内存。如果有数量较多的服务使用一个配置，热更新该配置时，进程内存可能暴涨。
20
21每个玩家一个 agent 代理引起的问题：
221、并发启动 agent 时，因 sharetable 服务中有一个，会形成单点问题
23解决：使用 agent pool 提前加载
24
252、热更新慢
26解决：使用小表多 key。因为 sharetable 服务的单点问题，agent 更新会排队，并不会造成进程 CPU 超负载，不放心可控制更新频率。
27
283、内存可能暴涨
29解决：sharetable.update 后 gc
30
31最终我选择，小表多 key 加 sharetable.update 热更新。
32选择理由：
331、使用方便，不会发生更新不到的情况。
342、历史原因。
353、热更新配置表频率低，只要不卡死进程，慢点可以接受。
36
37使用方式：
381、每个模块一个 key，小表多 key
392、每个玩家一个 agent 代理，使用 agent pool 提前加载
403、使用一个组播来通知热更新
414、所有服务初始化时必须加载需要使用的配置，保证业务在使用配置时不会挂起（可加一层接口封装实现）
425、服务收到热更新通知时，只更新初始化过的配置
436、sharetable.update 执行后 gc 一次
44
45小表多 key 加 sharetable.query 热更新也是很好的方案，做好不引用到 local 变量使用比 sharetable.update 方式更好。
46
47再次感谢大家的建议。
